# CyTube Development Guidelines

## Project Structure

- **`src/`**: Source code (ES6+ with Babel)
- **`lib/`**: Compiled output (generated by Babel, do not edit directly)
- **`test/`**: Unit tests using Mocha
- **`integration_test/`**: Integration tests using Mocha
- **`www/`**: Static web assets
- **`player/`**: CoffeeScript player modules that compile to JavaScript
- **`docs/`**: Documentation
- **`conf/`**: Configuration examples
- **`.agents/doc/`**: Planning and architectural documentation for features

## Build & Development Commands

Run all commands from the root directory:

- **`npm run lint`**: Run ESLint on `src/` directory
- **`npm run build-server`**: Compile `src/` to `lib/` with Babel
- **`npm run server-dev`**: Watch mode compilation with source maps
- **`npm test`**: Run unit tests (automatically runs lint first via pretest)
- **`npm run integration-test`**: Run integration tests
- **`npm run build-player`**: Rebuild player from CoffeeScript modules

## Code Conventions

### JavaScript/ES6+ Style

- Use `const` by default, `let` when variable is reassigned, avoid `var`
- Use arrow functions (`=>`) for callbacks and concise functions
- Use template literals for string interpolation
- Prefer `const { prop } = obj` for destructuring
- Always use JSDoc comments for public functions and complex logic
- Use meaningful variable names; avoid single-letter names except in obvious contexts (e.g., loop counters, mathematical formulas)

### Logging

- Use `@calzoneman/jsli` logger: `const LOGGER = require("@calzoneman/jsli")("module-name")`
- Include context: `LOGGER.info("Event occurred (channel: %s): %s", channelName, details)`
- Use appropriate levels: `LOGGER.debug()`, `LOGGER.info()`, `LOGGER.warn()`, `LOGGER.error()`

### Channel Modules

- Extend `ChannelModule` from `lib/channel/module.js`
- Modules should have a single, well-defined responsibility
- Register modules via `channel.modules["module_name"]` pattern
- Use optional chaining cautiously: `obj?.prop?.nested` to safely navigate optional chains

### Error Handling

- Create custom errors using the `create-error` package
- Include context in error messages for debugging
- Always propagate errors up the call stack, don't silently swallow them
- Use try-catch sparingly; prefer synchronous error handling where possible

### File Organization

- One principal class/export per file
- Group related utilities into modules
- Keep module files under 300-400 lines when possible; split into sub-modules if larger
- Import only what you need; avoid wildcard imports

## Testing

### Unit Tests

- Test file location: `test/{module-name}.js` for corresponding `src/{module-name}.js`
- Use Mocha test framework and Node.js `assert` module
- Test names should describe behavior: ✓ `constructs a camo url` ✗ `test camo`
- Organize tests with `describe()` blocks by module and function name
- Create mock/stub objects for dependencies; keep stubs simple with only required methods
- Use `assert.strictEqual()` for equality checks and `assert.deepStrictEqual()` for object comparison
- Test structure: Set up fixtures → call code → assert results (AAA pattern)
- Include edge cases, boundary conditions, and error scenarios
- Keep tests synchronous when possible (no callbacks/async unless testing async code)

### Running Tests

- `npm test` runs unit tests and lint checks (runs both mocha and eslint via pretest)
- Tests must pass before code is considered ready
- Never skip or ignore tests; if a test is flaky, fix the root cause

## Code Review Checklist

- [ ] Code follows the conventions above
- [ ] Tests are included and passing (`npm test`)
- [ ] No linting errors (`npm run lint`)
- [ ] Breaking changes are documented
- [ ] New public APIs have JSDoc comments
- [ ] Error handling is appropriate
- [ ] No console.log in production code (use LOGGER)

## Special Considerations

### Database Queries

- Use Knex.js for query building (avoid raw SQL when possible)
- Test database changes in isolation
- Document schema changes and migrations

### Socket.io Events

- Event names should be lowercase with hyphens: `message-sent`, `channel-update`
- Include validation of incoming socket data
- Test socket event handlers with appropriate mocking

### Redis Operations

- Use Redis module patterns established in the codebase
- Handle connection failures gracefully
- Document any assumptions about key structure or TTLs

### Async Code

- Prefer Promises and async/await over callbacks
- Handle Promise rejections properly
- Use try-catch in async functions for error handling

## Performance Considerations

- Profile critical paths before optimizing
- Cache frequently accessed data appropriately
- Limit database queries in loops; use batch operations when possible
- Monitor memory usage for long-running server processes

## Documentation

- Document architectural decisions in `.agents/doc/` for significant features
- Update relevant docs in `docs/` folder if adding new features or changing behavior
- Include JSDoc for public APIs
- Keep README.md and inline comments up to date
